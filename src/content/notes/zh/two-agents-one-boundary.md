我日常有两个 agent 同时在跑。一个负责工作场景，做深度分析：查知识库、跑长任务、写材料。另一个负责私人场景，做日常盯盘：盯市场行情、扫新闻、汇总到每天的简报里。

之所以分成两个，起因很朴素：两类任务对记忆的污染方向不同。盯盘 agent 每天产生大量碎片信息——报价、快讯、临时判断。如果这些和工作分析混在同一个记忆里，工作 agent 的上下文会被噪音稀释；反过来，工作里的长篇推理也不该挤进日常简报。所以两个 agent 的记忆完全独立，各自维护各自的上下文。

但资源是共享的。知识库、命令行工具、数据文件，两边都能用。分开的只有记忆，不是基础设施。

## 只读边界

真正让我花时间想清楚的，是权限怎么划。

我的做法是：私人 agent 对关键数据**只读**。它可以读取、可以分析、可以提醒，但如果一个结论需要写回关键数据——修改记录、更新结论库——它没有权限，必须经过工作 agent。

这条规则看起来不对称，理由在于两者的工作方式差异。盯盘 agent 的优势是高频、快速、便宜，代价是判断浅、上下文短，适合发现线索，不适合沉淀结论。工作 agent 慢，但每次运行都带着完整上下文和工具链，能做核查和追溯。让快的那个只负责「看到并报告」，让慢的那个负责「确认并落笔」，出错时的破坏半径就被限制住了。

这其实是组织设计里的老问题：一个团队里，谁有写权限，谁只有读权限，通常不由谁的算力强决定，而由谁的判断流程更严谨决定。Agent 团队没有本质区别。

## 边界是可以协商的

我没有把这条边界写死在架构里，它更像一条协作约定。有几类数据，私人 agent 的写入是无害的，比如它自己生成的行情摘要；另一些必须收紧，比如会进入工作结论的记录。边界划在哪里，取决于数据被写坏之后的修复成本。

这个经验推广一下：设计多 agent 系统时，与其先纠结框架和通信协议，不如先把职责表写清楚——每个 agent 负责什么、对哪些数据可写、对哪些只读、冲突时谁有裁决权。这些问题的答案定了，技术选型往往就只剩下实现细节。
